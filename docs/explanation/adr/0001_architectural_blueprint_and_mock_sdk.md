# ADR 0001: Architectural Blueprint and Telemetry Engine

## 1. Title
ADR 0001: Architectural Blueprint and Telemetry Engine

---

## 2. Status
**Proposed**

---

## 3. Context
We have separated the Elite Dangerous Journal/JSS SDK from the parent EDMarketConnector repository to manage its complexity independently. To prevent hand-coding 270+ discrete event classes, we need to design a **bi-directional, schema-driven Telemetry Engine** that handles validation, schema inference, and mock generation dynamically.

---

## 4. Decision

### 4.1 Core Telemetry Engine Design
We will implement a unified **`TelemetryEngine`** to serve as the core logic of the SDK. It will perform three base functions:
1. **Data-to-Schema (Inference):** Ingests raw JSON/JSONL strings from the game client and infers their JSON Schema.
2. **Schema-to-Data (Mock Generation):** Ingests a JSON Schema (or Pydantic model) and outputs a valid mock JSONL string populated with realistic values.
3. **Validation:** Checks raw data strings line-by-line against schemas to verify type and value constraints.

### 4.2 Bi-Directional Flow
The engine operates as a bi-directional data translator:

```mermaid
graph TD
    subgraph Data-to-Schema (Inference)
        A[Raw JSONL Log Line] -->|Ingest| B(Telemetry Engine)
        B -->|Infer & Scrub| C[Sanitized JSON Schema]
    end

    subgraph Schema-to-Data (Generation)
        D[JSON Schema / Pydantic Model] -->|Ingest| B
        B -->|Parse Types & Examples| E[Simulated JSONL Log Line]
    end

    subgraph Validation
        F[Log Payload] -->|Compare| B
        B -->|Assert Types| G[Pass / Fail Warning]
    end
```

### 4.3 Leveraged Tooling (No Re-inventing the Wheel)
To reduce code overhead, the engine will leverage established Python packages:
* **Validation:** **`jsonschema`** (standard Python engine for validating JSON against draft-04 up to 2020-12 specifications).
* **Inference (Data-to-Schema):** **`genson`** (a robust, standard library for generating schema models dynamically from JSON inputs).
* **Mock Generation (Schema-to-Data):** We will implement a lightweight generator using the standard library `random` and `json` modules that parses the schemas' `type` constraints and selects values directly from the `"examples"` arrays.

### 4.4 Ports & Adapters Architecture
We will implement the package layout under `src/ed_journal_sdk/`:

* **Core Domain (`src/ed_journal_sdk/domain/`):**
  * Houses pure Pydantic models generated by the schema compiler.
* **Telemetry Adapter (`src/ed_journal_sdk/telemetry/`):**
  * **`engine.py`**: The `TelemetryEngine` class.
  * `parser.py`: Log tailer and observer using the engine.
* **Testing Simulator Adapter (`src/ed_journal_sdk/testing/`):**
  * `writer.py`: Houses `FileJournalWriter` (filesystem output).
  * `generator.py`: Mock value wrappers driving the engine.

### 4.5 Scratch Usage Blueprint
We define the target developer usage API for the Telemetry Engine:

```python
from pathlib import Path
from ed_journal_sdk.telemetry.engine import TelemetryEngine
from ed_journal_sdk.testing.writer import FileJournalWriter

def run_simulation() -> None:
    # 1. Initialize Telemetry Engine (Logic) and File Writer (I/O)
    engine = TelemetryEngine()
    writer = FileJournalWriter(output_dir=Path("./data/simulated"))

    # 2. Schema-to-Data: Generate a mock FSDJump JSONL string using the schema
    fsd_schema = engine.get_schema("FSDJump")
    mock_line = engine.generate_line(schema=fsd_schema, overrides={"SystemName": "Sol"})

    # 3. Data-to-Schema: Ingest a raw line and infer schema
    raw_sample = '{"timestamp":"2026-08-20T00:00:00Z", "event":"Docked", "StationName":"Jameson"}'
    inferred_schema = engine.infer_schema(raw_sample)

    # 4. Validation: Verify a line matches its schema
    is_valid = engine.validate_line(raw_sample, inferred_schema) # Returns True

    # 5. Write outputs to disk using the File Writer adapter
    writer.start_game(cmdr_name="Cmdr Jameson")
    writer.write_raw_line(mock_line)
    writer.stop_game()

if __name__ == "__main__":
    run_simulation()
```

## 5. Consequences

### Positive:
* **Dynamic Modularity:** Any new game events added by Frontier are instantly supported by the engine without new Python classes.
* **Low Maintenance:** Leveraging `jsonschema` and `genson` cuts our codebase development overhead by 90%.

### Negative:
* Introduces third-party dependencies (`jsonschema`, `genson`) to the project.
